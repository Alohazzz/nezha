### 页 0 · 封面

### 页 1 · 为什么需要 Nezha（开场，权重 5%）

**讲法**：先立产品身份，再转到问题。

- 一句话讲清时代变化：*「人写的代码越来越少，AI 写的代码越来越多，写代码本身开始变成一件可以并行的事。」*（README 原文，可直接引用）
- 讲清 Nezha 的答案：**Agent 优先设计**——内置终端直接跑原生 Claude Code / Codex，并在此之上集成任务系统、Git、Worktree、终端、代码编辑器。
- 收在痛点钩子上：*但「能并发」不等于「能交付」*——引出下一页。

### 页 2 · 问题：流程断裂（总纲，权重 8%）★核心页

**一句话痛点**：**议题在云效、代码在 Git、审查在线下、知识在会话里——四套东西、四个地方，全靠人肉搬运。**

展开成四条「断点」，每条对应后文一节功能：

| # | 断点（Before） | 后果 | 后文对应 |
|---|---|---|---|
| 1 | 议题在云效，方案讨论在聊天/口头，结论不留痕 | 执行时反复确认、返工 | ① 云效议题闭环 |
| 2 | 多条议题谁先谁后全靠人记，串行执行经常排错序 | 前置没做完就开跑，返工空转 | ① 依赖门禁 |
| 3 | 分支散落各处，谁该合、合到哪、能不能收尾靠翻 | 分支积压、漏合并 | ② 计划与合并请求 |
| 4 | 审查意见散在本地，讨论中确认的知识随会话流失 | 知识不沉淀、下次重讲 | ③ 合并审核 / ④ 知识沉淀 |

**落一句话**：Nezha 要做的，就是**把这条链路接成一条闭环**。

### 页 11 · 三大亮点 ★核心页（权重 5%）

**建议做成一页高潮页**：三条并列，最亮的（依赖门禁）视觉权重最大。

1. **依赖门禁**——编排与批处理的分界线：拓扑排序串行放行，前置未完成的任务停在 `waiting_deps` **不创建 PTY**（不空转），前置失败**不静默跳过**（标红 + 只通知一次 + 由人决定忽略或等待）。
2. **方案双契约**——讨论阶段不写代码，产出两份可移交文件：`plan.md`（人读的方案）+ `deps.json`（机器读的依赖契约）。
3. **回写闭环**——任务完成自动生成「开发向 / 测试向」双评论，事实骨架带 commit 哈希与变更统计，AI 润色失败回退模板，幂等不重复回写。**这是云效上那 73 条的物理形态。**

> 三条的关系：前两条是**方法论**（编排 + 把关），第三条是**可被数据证实的结果**。

### ① 云效议题闭环（权重 30%，全篇最重）[→页 6–8]

**解决的问题**：
> 场景——「在云效上看到一条 bug，想交给 AI 修。得先把议题描述复制出来、手动提炼成提示词、开终端、等它跑完、再回云效手动写一版『改了啥』的评论。中途想先出个方案看看？没有地方放。」

**关键行为**（按操作顺序）：

1. **连接与浏览**：填云效令牌（`pt-xxxx`）→ 获取组织 → 选项目 → 保存。议题区支持类别 Tab（全部/需求/任务/缺陷）、项目切换、状态多选、只看我负责的、搜索、分页（每页 100）。
2. **两个入口**（议题行右侧）：
   - **直接开始**——跳过讨论直接执行，议题描述即 spec；
   - **发起讨论**——进入方案讨论链路（先出方案再执行）。
   - 「已导入」是去重标记，不是一个可点的导入操作。
3. **直接开始的工作流路由**（按类别自动分流，无需人工选）：

   | 议题类别 | 勾选状态 | 实际工作流 |
   |---|---|---|
   | 缺陷（Bug） | 复选框不出现 | 先 `diagnosing-bugs` 定位根因（要有可复现证据）→ 再 `implement` |
   | 需求 / 任务 | 不勾（默认） | 直接 `implement`，议题描述即 spec |
   | 需求 / 任务 | 勾「先做需求澄清」 | 先 `grilling` 一次一问澄清 → 达成共识后立即 `implement` |

4. **发起讨论**：打开对话框**即已创建 draft 方案**，议题详情与图片归档到 `.nezha/plans/<planId>/`；讨论阶段**先不写代码**，产出 `plan.md` + `deps.json`。已有定稿方案时可把它挂成**子方案**。
5. **方案定稿后两个按钮**：「开始」（生成待办并立即按拓扑顺序串行跑）/「生成待办」（只生成 `todo`，人工把关后再跑）。
6. **方案看板**：`Alt+K` / `⌘+K` →「方案」标签页；左栏方案列表（进度 + 状态筛选），右栏**依赖关系图**（左→右 = 执行顺序）+ 拓扑排序的任务行。生命周期：标记完成 / 重新打开 / 取消（留存态，不删除）/ 归档 / 删除（有引用时后端拒绝）。
7. **依赖门禁**（`deps.json`）：见「亮点 H2」。
8. **追加议题**：一批新议题合成一个**子方案**挂在主方案下，看板上缩进显示，跨方案依赖渲染为外部节点。
9. **补录议题（反向闭环）**：运行中发现新问题 → 调 `yunxiao-backfill-issue` 技能 → Agent 盘问（先问「缺陷还是需求」）→ 用户确认（人工闸）→ 写 `.nezha/drafts/<taskId>/backfill-issue.json` → **持有令牌的后端**调 `CreateWorkitem` 建云效议题 → 自动创建绑定该议题的本地 `todo` 任务。
10. **回写云效（正向闭环收口）**：见「亮点 H3」。

**亮点**：

- **H1 · 方案双契约** [→页 11 三大亮点]
  讨论阶段不写代码，产出两份可移交文件：`plan.md`（人读的方案）+ `deps.json`（机器读的依赖契约）。「先出方案再执行」不是口号，是两份**可移交的文件**。

- **H2 · 依赖门禁** [→页 11 三大亮点]
  - 拓扑排序串行放行；前置未全部 `done` 的待办停在 **`waiting_deps`**，完成后**自动放行**；等待中**不创建 PTY**（不空转资源）。
  - 前置**失败/取消/中断/缺失**时**不静默跳过**：继续等待、看板**标红**、**只通知一次**，由人决定「忽略依赖，仍然开始」。
  - 放行受每项目并发上限 `[plan] max_concurrent`（**默认 1 = 串行**）约束；「忽略依赖」只绕过前置判断，**不**绕过并发上限。
  - 解析刻意宽松（防死锁）：文件损坏只是少一道护栏（告警降级）；依赖成环时**环上的边全部丢弃**。
  - 门禁**只作用于方案待办**，普通任务行为不变。

- **H3 · 回写闭环 + 价值评分** [→页 11 三大亮点]
  - 任务 `done` 且云效绑定时出现「回写云效」按钮，卡片显示「待回写」徽标。
  - 生成两条评论：**开发向**（改动内容 + 价值评分由来）/ **测试向**（影响范围与测试指引）；事实骨架含议题编号/标题、**关联 commit 短哈希 + 提交信息、变更统计**；再由 headless Agent 润色，**AI 失败时回退为纯事实模板**。
  - 预览可编辑、可重新生成；确认后发布，价值评分同时写入云效字段（写失败可「补写字段」）。
  - 记录 `yunxiaoWrittenBackAt` / `yunxiaoCommentId`，保证**幂等，不重复回写**。

### ② 计划与合并请求（权重 25%）[→页 9]

**解决的问题**：
> 场景——「一个需求拆成 5 个议题做完，改在 5 条分支上（或者在同一个分支上先后提交），现在要合回 develop。哪条分支该合、合到哪、有没有漏、能不能删，得自己翻 git log 加云效平台两边对着看。」

**关键行为**：

1. **计划 = 一组有序议题 + 一条分支 +（可选）一个 worktree**。
   - 创建对话框字段：计划名称、类型（`feature`/`fix`/`patch`/`project`/`hotfix`）、版本（可从云效版本取，自动去掉尾部 `.0`）、源分支（按 `类型/版本/目标分支/描述` 自动生成，可手改，点「检测」校验重名）、基础分支、合并回目标分支、**另建 worktree**（默认不勾，直接切主工作区）。
2. **状态徽标全自动流转**：`进行中`（创建即此）→ `待评审`（提交 MR 后）→ `已合并`（MR 合并后）；删除/关闭落 `已关闭`。附带徽标：主检出 / WorkTree 缺失 / 运行程序缺失 / **超期**（>14 天未合并/关闭）。
3. **议题表状态与方案关联全自动派生**（无手动维护入口）：已完成 / 执行中 / 已结束 / 讨论完成 / 讨论中 / 未开始，自上而下取第一个命中。
4. **「发起合并」视图**（为**无计划记录**的分支发起 MR）：欢迎页左侧进入。
   - **分段加载**：先做文件系统级仓库发现（无 git 子进程，秒回）→ 选了仓库才扫该仓库分支（一次全扫要几十秒，所以不自动全扫）。
   - 列表只收「**已推送 + 有未合并提交 + 无开放 MR**」的候选分支。
   - 行徽标：已合并进 X / 部分合并 / 未合并；无 MR / 已有 MR #N / MR 未知；我的提交；受保护；数据缺失。
   - **目标分支推断**（四级）：手动指定（跨会话记住）> 项目配置 > 按分支名推断（如 `hotfix/…/master/…` → `master`）> 默认值（develop/master/main 里最像主干的）。改一行只重算该分支。
5. **批量发起合并请求**：勾选 → 确认层逐条列出「分支 → 目标分支」+ 审核人 → 逐条推源分支（非强制）→ 调 Codeup 建 MR。已有「同源 + 同目标」开放 MR 的**自动跳过（幂等）**；单条失败**不中断整批**，逐条回执。审核人查不到时**明示失败原因**而不静默创建无评审人的 MR。
6. **批量删除远端分支**：两阶段（dry-run 扫描 → 确认框 → 执行），逐条回执。

**亮点**：

- **H4 · 分支库存 × 平台数据 join**
  把本地分支元数据与云效平台数据拼在一起，一眼看清「哪些分支还没发起 MR、该合到哪、是否已可收尾」——把「翻两边对照」变成「看一个列表」。

- **H5 · 硬门禁的批量操作**

### ③ 合并审核（权重 15%）[→页 10 前半]

**解决的问题**：
> 场景——「同事发来了 MR，你得切到本地、拉分支、读完 diff、在云效上写评审意见。一次两次还行，MR 一多就是纯体力活。」

**关键行为**：

- 欢迎页左侧「合并审核」进入集中列表，顶部「全部仓库」下拉筛选 +「刷新」。MR 卡片显示状态徽标（评审中/待合并/已合并/已关闭/已通过 + 有冲突）、`源分支 → 目标分支`、仓库、作者、审核人。
- **四个操作**：

  | 操作 | 作用 | 说明 |
  |---|---|---|
  | 拉取代码 | 把 MR 源分支拉到本地临时仓库 | 完成后变「重新拉取」；**合并前必须先做** |
  | 代码审查 | 启动 Agent 任务，按 `merge-code-review` 技能出审查报告 | 任务名形如 `代码审查 <标题>` |
  | 分支合并 | 启动 Agent 任务，把源分支合并并推送到目标分支 | 需先拉取代码；报告含阻止级 `fail` 会二次确认 |
  | 查看审查结果 | 打开审查报告弹窗 | 无报告时提示先做「代码审查」 |

- **审查报告**可「回写到评论」（先进可编辑态，带字数提示 → 确认后作为整体评论发布到云效 MR）/「复制」/「导出 .md」。
- 临时仓库默认在 `~/.nezha/codeup_worktrees/`（可改）；认证复用云效令牌。

> **重要澄清（讲稿要诚实说明）**：「代码审查」「分支合并」都是**启动真实 Agent 任务**，不是直接调平台 API 一键完成；合并最终由 Agent 在本地 git 推送（默认 fast-forward，不 force）。

**亮点**：

- **H6 · 审查报告一键回写**
  Agent 出报告 → 可编辑 → 一键发成云效 MR 评论。「审查意见」不再散在本地、不用手动复制粘贴。

### ④ 知识沉淀 + 知识图谱（权重 20%，合并为一节）[→页 10 后半]

> **为什么合并**：两者在手册里就是上下游——沉淀从会话**提取**候选知识并创建云效审核议题，图谱负责**承载**这些知识（模块卡片）。分开讲会互相打断，合起来才是「知识闭环」。

**解决的问题**：
> 场景——「跟 Agent 讨论了两小时，把某个业务的坑讲明白了，任务做完，会话一关，这些结论就散在几百行 JSONL 里。下次换个 Agent 还得重讲一遍。」

**关键行为（沉淀侧）**：

1. **入口**：任务 `done` 且云效绑定时，详情头部出现「沉淀知识」按钮。
2. **生成候选**：后端读取 `knowledge-sedimentation` 技能注入 headless prompt；输入含会话摘要（约 8000 字截断）、云效议题字段与链接、图谱 data 目录（现场比对）、项目根代码（用于 `rg` 验证依据）。按「卡片六段骨架」判定优先级（业务规则/已知坑 > 关键实体/表映射 > 职责修正/依赖补充 > 验证记录），**门槛 = 有依据**（代码/文档/用户确认）；排除图谱已有内容、无依据猜测、纯实现细节。输出标签化 JSON（模块/段落/内容/依据/置信度/建议标题）。
3. **预览与编辑**：弹窗逐条可改内容、依据、标题、置信度，可勾选要创建的候选；无有效候选时提示可「重新生成」。
4. **创建审核议题**：逐条创建到**「知识库图谱」项目**；标题格式 `【知识沉淀】<模块id>-<知识点摘要>`；描述固定模板（来源议题→目标模块卡片→建议更新段落→具体内容→依据→置信度→审核指引）；**创建前按标题关键词去重**。
5. **自动回写（可选开关，默认关）**：
   - **关闭**：知识只到「创建审核议题」，审核通过后由知识库负责人人工更新卡片并提交推送。
   - **开启**：创建议题后立即对「已确认」且有依据的条目跑**回写质量门**；全部通过则**追加**写入项目绑定的图谱模块卡片、推送技能库、把议题置为「已完成」。**只增不改**（追加到匹配段落末尾），且**不覆盖卡片尚未提交的手工改动**。

**关键行为（图谱侧）**：

1. **浏览/编辑**：项目右侧工具栏「知识库」面板展示绑定图谱的模块卡片，顶部「提交并推送(N)」，有未提交改动带「已改」标记；点卡片以 Markdown 页签打开可编辑（自动保存）。
2. **绑定与维护**（项目设置 → 知识库）：下拉绑定图谱；「扫描项目」跑 `bootstrap.py --mode scan` 依据代码重建 `index.md`/`graph.json`（**已有卡片不被覆盖**）；「管理模块卡片(N)」可新建/编辑/重命名/删除卡片；「新建图谱」填 ID/名称/适配器。
3. **数据约束**：图谱数据由技能仓库统一管理（`knowledge-graphs/<图谱ID>/graph.toml` + `data/modules/*.md`）；项目绑定写在 `.nezha/config.toml` 的 `[knowledge] graph_id`；数据由 **git 统一管理**（可 revert 回滚）。

**亮点**：

- **H7 · 知识不随会话流失**
  会话里确认的增量知识 → 提取 → **云效审核议题**（有审核人把关）→ 可选的**质量门 + 自动回写**。自动回写「只增不改」、不覆盖人工未提交改动——**自动化但没有失控**。

- **H8 · 图谱是 Agent 的认知底座**
  模块卡片让 Agent 讨论前先看项目知识，沉淀完又回填卡片——**喂养与回收是同一个池子**。这是「越用越懂你们项目」的机制。

### ⑤ 工程支撑：技能管理（权重 10%，轻量收束，构建一笔带过）[→页 10 尾]

**解决的问题**：
> 场景——「技能散在各项目目录里，改了 A 项目的技能，B 项目还是老版本；想统一维护，又没有地方放。」

**关键行为（技能管理）**：

1. **来源**：本地目录，或 git 远端（仅允许 `https://` / `git@`）。首次完整 `git clone`（**不用浅克隆**，以便图谱可 `git revert` 回滚）到 `~/.nezha/skill_repos/<sanitized>/`；已存在则 `git fetch` 探测变更，**有变更才** `--ff-only` 拉取（不 `reset`、不覆盖本地改动）。**启动后每 15 分钟自动拉取**，失败静默沿用缓存并退避，来源标记 `stale`。
2. **安装 = 软链**：装到项目/全局的技能是**软链**，指向 Hub 内目录——Hub 更新后已安装技能**自动跟随，无需重装**。健康标记：`ok` / `broken`（目标丢失）/ `diverged`（路径被外部修改）。
3. **数据管理**：技能若带数据目录（如 `his-knowledge-graph/data/`），可打开文件夹/备份/重新构建；由 `NEZHA_SKILL_DATA_DIR` 等环境变量注入，随仓库 git 管理。
4. **清理**：清理失效安装**只删软链与安装记录，不删普通目录**；删除技能有二次确认。
5. **SkillHub 即项目**：技能库注册为一个特殊项目，可在普通任务/文件/终端视图里编辑技能内容。

**亮点**：

- **H9 · 软链安装、零成本跟随**
  装到项目的是软链，Hub 更新即全量生效；git 远端每 15 分钟自动同步，失败静默沿用缓存。「一处维护，处处最新」。

## 附录 B · 事实核对清单（防错）

制作时容易写错的点，已逐条核对：

| 易错点 | 正确事实 |
|---|---|
| 依赖门禁跳过前置失败 | **不静默跳过**——标红 + 只通知一次 + 由人决定 |
| 等待中的任务 | **不创建 PTY**（不是「创建后挂起」） |
| 并发上限默认值 | `[plan] max_concurrent` **默认 1 = 串行** |
| 「取消方案」 | 是**留存态**，不删除；删视野用「归档」 |
| 补录议题落成什么 | 落成 **`todo`，不会自动启动** |
| 云效令牌存哪 | `~/.nezha/settings.json`；**不写入代码/日志/仓库，Agent 进程不持有**（所有写操作由后端代劳） |
| 「代码审查/分支合并」 | 是**启动真实 Agent 任务**，不是一键调 API |
| 合并推送方式 | 默认 **fast-forward，不 force** |
| 技能安装方式 | **软链**，Hub 更新自动跟随；**不用浅克隆** |
| 同步策略 | **有变更才** `--ff-only` 拉取；**不 reset、不覆盖本地改动** |
| 自动回写语义 | **只增不改**；**不覆盖卡片尚未提交的手工改动**；**默认关闭** |
| 删远端分支门禁 | 只有**已完整合并进目标分支**的才可删；**只删远端，不删本地** |
| 批量发起 MR 幂等 | 「同源 + 同目标」已有开放 MR 的**自动跳过** |
| 构建 | **本轮不单独成节**，一笔带过 |
| 主题数量 | 4 种：dark / midnight / light / eyecare（README 只展示了 3 种，别写成「3 种」） |

## 附录 C · 制作提示（给下游 HTML Agent）

1. **叙事优先于功能**：按 Part 1 的顺序讲，**不要**把六节平铺成六个等大模块。①占总篇幅 30%，⑤只占 10%。
2. **数据页是王牌**：放在功能线**之前**（页 4）。先把「成了」给到，再讲「怎么成的」。
3. **动图优先投屏**：`docs/screenshots/operation-manual/` 下 6 个 GIF 是流程演示的最佳素材。
4. **暗/亮双主题**：截图大多有暗+亮两版，可做主题切换或并排对照（nezha 本身有 4 主题，这是产品特性）。
5. **配图分辨率**：截图多为应用界面截图，注意裁切比例；GIF 需确认体积（投屏加载）。
6. **不要编造**：所有数字以附录 A 为准；所有功能行为以 Part 2 与 `docs/operation-manual.md` 为准。
7. **可内嵌手册**：若需要「了解更多」，可用 iframe 内嵌 `public/help/operation-manual.html?embed=1`（需先跑 `pnpm help:sync`）。
