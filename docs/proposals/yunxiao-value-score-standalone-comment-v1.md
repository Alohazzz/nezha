# 提案：价值评分独立成第三条评论（dev / test / score 三分离）

> 状态：**提案草稿**。目标评审方为内部团队（Codeup / 云效项目），**不向上游 GitHub 仓库提交**
> （上游仓库已与本 fork 无关，AGENTS.md 的 issue-first 流程仅在内部流程中执行）。
> 依据：QHDK-30560 字段失效排查（2026-10-10，修复见 `merge_plan_writeback_draft` 整份草稿提取 + 回归测试）。
> 本文件只描述动机与范围，不含实现。

---

## 1. 现状与问题

### 1.1 现状结构

「回写云效」目前发布**两条**评论，评分小节寄生在开发向评论里：

```
开发向评论 = 修改方案汇总 + ## 价值评分（含 7 维表格、指数推导、否决检查、定级）
测试向评论 = 影响范围与测试（修改分支 / 修改文件 / 测试步骤）
议题字段   = 价值评分（Req 核心指数 / Bug 优先指数），从开发向评论正文解析
```

草稿 `discussion.md` 的小节顺序按技能契约固定为
`修改方案汇总 → 价值评分 → 影响范围与测试`（自动生成来源），
回写时按 `## 影响范围与测试` 标题一刀切成 dev / test 两个半区。

### 1.2 已发生的失效（QHDK-30560，2026-09-28）

执行 agent 把「## 价值评分」写在了「## 影响范围与测试」**之后**（违反技能契约顺序）。
切分后评分小节落进 test 半区，旧代码只从 dev 半区提取评分：

- 开发向评论缺评分小节 → 回写命令解析不到指数 → **字段不写**（仅一条易忽略的 warning）；
- 评分小节却随测试向评论发布 → 云效上「评论有评分、字段无值」。

已修复（提取改为整份草稿 + 顺序颠倒回归测试），但这是**防御 agent 不守顺序**，
根因是「评分归属靠字符串切分决定」这一结构耦合，同类风险仍存在：

| 残留风险 | 场景 |
|---|---|
| 重新生成丢评分 | force 重新生成需先保留旧草稿评分小节再拼回（`preserved_score_section`），任何一环遗漏即丢 |
| 字数上限连锁失败 | 评分大表（~2KB）挤占开发向评论 `MAX_COMMENT_CHARS` 上限，超限则**整次回写失败**，评论都发不出 |
| 解析来源可被用户破坏 | 字段值从 dev 评论正文解析；用户在弹窗里编辑 dev 预览（如删掉评分小节）→ 字段静默失效 |
| 顺序契约持续消耗 | 技能文档需维护两种来源的顺序规则 + 结构自检条款，agent 每次执行都是一次可违反的约束 |

## 2. 提案：评论结构改为三条

```
开发向评论 = 修改方案汇总（纯 What/Why/Scope）
测试向评论 = 影响范围与测试
评分评论   = ## 价值评分 完整小节（7 维表格 + 指数推导 + 否决检查 + 定级 + 一句话结论）
议题字段   = 价值评分，从评分评论（独立输入）解析
```

发布顺序 dev → test → score（评分放最后，弱化评论区噪音）。

### 2.1 收益

1. **结构上消灭顺序耦合**：评分独立成输入后，`split` / `reappend` / `strip` 的提取拼回逻辑退化为
   「从整份草稿提取一次」，草稿小节顺序自由，技能契约可删掉顺序规则与自检条款——agent 少一个可犯错的约束。
2. **重新生成天然安全**：dev/test 重新生成不触碰评分评论，无需保留-拼回机制。
3. **字数解耦**：三条评论各自独立计限，大表格不再可能把 dev 评论顶到超限。
4. **解析来源唯一且可见**：弹窗三个预览框对应三条评论 + 字段值，缺哪个看得见，不存在「编辑正文误伤字段解析」。
5. **云效阅读动线**：改了什么 → 怎么测的 → 为什么值这个分，评分作为管理者视角信息独立可扫读。

### 2.2 明确不解决的问题（诚实边界）

- 评论区条数 +1/议题：接受（见发布顺序弱化）。
- 评分细节展示：**现状已满足**——表格已随开发向评论完整发布，富文本转换正常，这不是本提案的收益来源。

## 3. Scope（影响面）

| 层 | 改动 |
|---|---|
| 后端 `yunxiao.rs` | `yunxiao_writeback_with_score` 增加 `score_content` 输入（可空=不发布评分评论，兼容旧调用）；`YunxiaoWritebackResult` 增加 `score_comment_id: Option<String>`；字段解析来源改为 `score_content`；失败语义：score 评论失败归入 warning + 补写入口模式（dev/test 已发的部分成功态） |
| 后端 `agent_assist.rs` | 草稿拆分产出三段（dev / test / score）；`merge_plan_writeback_draft` 同步三分离；本次已修的「整份草稿提取评分」直接复用为旧草稿兼容层 |
| 技能契约 | `yunxiao-issue-execution`（discussion.md 结构：评分小节位置改为「任意位置，回写时独立提取」）、`issue-value-scoring`（写入位置描述）；经 SkillHub 同步 |
| 前端弹窗 | `YunxiaoWritebackDialog` 两个预览框 → 三个（score 预览默认只读可折叠，避免弹窗过高）；`retryScoreValue` 重试入口语义不变 |
| i18n | 新增 score 预览框标签等文案（zh + en） |
| 测试 | 回归：三条发布顺序、score 评论失败的部分成功态、旧格式草稿（评分在正文内）兼容、弹窗三预览渲染 |

## 4. 兼容性

- **旧草稿**（评分在 discussion.md 正文里）：提取逻辑保留（本次修复已实现），发布时拆出为第三条评论。
- **旧议题数据**：不追溯。QHDK-30560 的字段值（31.5）仍需人工补写一次（应用内补写入口或 API）。
- **API 语义**：`score_content` 为空时不发布第三条评论、不写字段，行为与「草稿无评分小节」等价，向后兼容。

## 5. 不做 / 暂缓

- 不做评分评论的独立编辑器（首版只读预览 + 重发，编辑需求出现再说）。
- 不改字段写入的 API 载荷形态（字符串值实测 204 成功，无需动）。
- 不在本提案内处理「评论条数噪音」的进一步优化（如折叠/引用），等云效侧反馈。
