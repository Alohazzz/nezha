## 0. 为什么需要修订

现状的知识组织规则散落在**三处**，且已经互相矛盾：

| 位置 | 内容 | 问题 |
|---|---|---|
| `src-tauri/src/agent_assist.rs:512` `KNOWLEDGE_SEDIMENTATION_RULES` | 提取规则（内嵌进提示词） | 要求 agent **标注冲突**「与现状冲突，需复核」 |
| `knowledge-graph/SKILL.md`（SkillHub） | 同一份 section 清单 + 「回写质量门」六条 | 门已改由 Nezha 侧四层实现，此处六条**已失效**却仍在 |
| `src-tauri/src/knowledge.rs:919` | 写入卡片的条目格式 | 写入恒定无信息的「· 已确认 ·」 |

**核心矛盾**：提取规则要求 agent 把「与图谱冲突」的结论提出来供复核，但四层门按产品决策**一律拒绝冲突**，且失败出口尚未落地（ticket 08）⇒ 冲突知识被提出 → 被拒 → **没有任何出口**，而 agent 还被要求标注它。

**本次修订的两条决策**（已确认）：
1. **冲突知识不提**——与门一致，从源头消除死胡同。
2. **条目保留两行结构、去掉「· 已确认 ·」**——该标记是恒定值（只有 `confirmed` 能过门），不携带信息。

## 1. 提取规则（修订版，可直接替换 `KNOWLEDGE_SEDIMENTATION_RULES`）

```
知识沉淀规则：
- 只提取「长期有效的项目知识」，按价值排序：业务规则/已知坑 > 关键实体/数据表映射 > 模块职责修正/依赖补充
- 必须有可定位的依据（真实存在的代码文件/文档位置，或明确的用户确认）；无依据一律不提
- 排除图谱已有内容；排除纯实现细节（代码怎么写的，而非项目怎么运行的）
- 若你的结论与图谱已有内容矛盾：**不要提取该条**（图谱已有其一，孰对孰错无法在此判定，留给人工）
- section 限定（必须是目标卡片中已存在的标题）：职责 / 关键实体与数据表 / 依赖与相关模块 / 业务规则与已知坑 / UI界面与入口
- 一条候选只表达一个知识点；内容与依据都必须是单行（换行会被拒收）
- 每条必须显式表态：有知识就产出候选；确实没有新知识时产出空数组并说明原因
- JSON 示例：[{ "module": "<目标知识库中的模块名>", "section": "业务规则与已知坑", "content": "…", "evidence": "…", "confidence": "confirmed" }]
```

### 相对现状的改动

| # | 改动 | 理由 |
|---|---|---|
| 1 | **删除**「与图谱冲突的结论标注『与现状冲突，需复核』」，改为「矛盾则不提」 | 与四层门「冲突一律拒」一致；原规则制造了无出口的冲突知识 |
| 2 | **删除** `验证记录` 作为可写 section | 它按规范是「日期 + 依据 + 内容」的流水记录，由扫描/人工维护；沉淀写进去语义重复（写入块本身已带日期与依据） |
| 3 | **删除** `定位` 作为可写 section | `module-card-guide.md` 明确「保留 `## 定位` 自动生成部分」；该段由扫描生成（业务领域/代码路径/工程数），沉淀不应改它 |
| 4 | **删除** `suggestedTitle` 字段 | 现状从未被使用（不写入卡片、不参与去重），是死字段 |
| 5 | **明确**「单行内容」 | 换行会伪造 `## ` 标题注入卡片结构（已由门拒收），须在规则里前置说明，避免 agent 白产 |
| 6 | **明确**「必须显式表态」 | 支撑「文件缺失 = 漏了」与「显式 skipped」的区分（ticket 01/11） |
| 7 | **明确**「一条候选只表达一个知识点」 | 门按条判定；一条混装多个知识点时部分错误会拖累整条 |

> `confidence` 字段**保留**：它仍是门的入口条件（只有 `confirmed` 可自动写入），但不再写入卡片正文。

## 2. 候选 schema

```json
{
  "module": "Nto.His.Register",
  "section": "业务规则 / 已知坑",
  "content": "锁号逻辑：SchedulId 可选——为空则遍历排班锁定，非空则直接锁定指定排班",
  "evidence": "Nto.His.Register/Nto.His.Register.Bll/Controller/LockNumController.cs:60-61",
  "confidence": "confirmed"
}
```

| 字段 | 约束 | 用途 |
|---|---|---|
| `module` | 目标卡片必须**已存在**（沉淀不新建模块） | 决定写入哪张卡 |
| `section` | 必须是该卡片**真实存在**的标题（归一化后匹配） | 决定写入哪一节 |
| `content` | 单行、非空、规范化后非空 | 知识正文 |
| `evidence` | 可定位：真实文件路径（推荐带行号）/ 目录 / 工程名 / 用户确认 | 写入正文 + **L1 确定性核验** |
| `confidence` | `confirmed` 可自动写入；`pending` 一律拒绝 | 门的入口条件 |

**取消**：`suggestedTitle`（死字段）、`knowledgeGraphId`（改由 Nezha 从项目配置兜底填入，不再要求 agent 写——现状该字段不一致会丢弃整份草稿，是纯失败源）。

## 3. 写入卡片的条目格式（修订版）

```markdown
## 业务规则 / 已知坑

- 2026-09-16 · 缓存键必须带租户前缀
  - 依据：Hsp.BaseData.Cache.Bll/CacheService.cs:42
```

**改动**：去掉恒定的 `· 已确认 ·`。

| | 现状 | 修订后 |
|---|---|---|
| 主体行 | `- 2026-09-16 · 已确认 · <content>` | `- 2026-09-16 · <content>` |
| 依据行 | `  - 依据：<evidence>` | 不变 |

**为什么不改成与存量卡片完全同风格**：存量人工条目把来源内联在句内（`（来源：提交，2026-08-24）`）。若沉淀也这样写，**自动写入与人工编辑的条目将无法区分**，ticket 08 要求的「事后能看出哪些是自动写入、便于按标记回滚」就无法实现。保留独立「依据」行，是刻意让自动条目**可识别**。

**顺带的良性性质（实测确认）**：`normalize_knowledge_text` 本来就把「已确认 / 待验证 / 来源 / 括号标注」当噪声剥掉，所以去掉 `已确认` **不影响 L2 去重判定**，不需要迁移。

**已知限制（保留记录）**：一条沉淀只能是「单行内容 + 单行依据」，多段落的复杂知识必须拆成多条。

## 4. 与四层门的关系

规则文本只负责**让 agent 产出合格候选**；判定由 Nezha 侧四层门完成（详见规格 §5）：

| 层 | 判什么 | 与本节规则的关系 |
|---|---|---|
| L0 结构 | 字段、`confidence=confirmed`、模块名、section 真实存在 | 规则的「section 限定」由此强制执行 |
| L1 依据核验 | 依据文件存在、行号在范围、断言里的代码标识符可定位 | 规则的「必须有可定位依据」由此强制执行 |
| L2 去重 | 规范化哈希相等即拒 | 规则的「排除图谱已有内容」由此强制执行 |
| L3 语义 | duplicate / conflict / distinct，双跑一致 | 规则的「矛盾则不提」在此兜底（即使 agent 提了也会被拒） |

即：**规则是提示，门是执法**。规则与门一致时，agent 不会白产；即使 agent 违反，门仍会拦下。
