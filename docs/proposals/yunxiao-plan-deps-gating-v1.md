## 1. 要解决的问题

多议题联合方案的讨论任务会在 `## 统筹` 节里分析「跨议题依赖关系 + 建议执行顺序」，但这些结论**只以散文形式留在 `plan.md` 里**：

- `Task` 结构体没有任何依赖字段（`types.ts` 与 `storage.rs` 均无），任务之间也没有批次承载串行关系——「生成待办」明确是「普通 todo，跑在当前工作区，不自动建批」（`App.tsx` 生成待办处注释）。
- 共享工作区放大后果：这批待办跑在同一份工作区（不建 worktree），前置未完成就并行开展，不只是 git 冲突——后继任务会在**半成品代码**上继续改，产出互相覆盖。
- 顺序结论丢失：确认页排序只是落成 `createdAt = now + i`，没有独立字段承载；而任务列表按 `updatedAt/createdAt` **倒序**排（`task-panel/TaskList.tsx`），等于顺序被抹平。更甚者，确认页初始顺序来自**你在云效列表里勾选议题的先后**，与统筹节写的「建议执行顺序」完全脱节。
- 统筹节的软约束无强制力：讨论提示词已要求 agent 分析依赖与顺序，但产出是给人读的散文，Nezha 既读不到也无法校验。

**结果**：方案里已论证过「B 必须在 A 之后」的议题，仍然和 A 一起开展，改到同一区域代码、互相踩。

## 2. 期望行为（一句话）

方案讨论额外产出 **`deps.json`** 机器可读依赖文件 → 生成待办确认页可视化/可编辑 → 点击开始时若有未完成前置则进入新状态 **`waiting_deps`** → 前置 `done` 后**自动接续**，同项目**默认串行**。

## 3. 决策清单（核心，逐条可批注）

| 编号 | 决策点 | 结论 | 理由 |
|---|---|---|---|
| **D1** | 依赖数据来源 | 讨论任务落盘**独立 `deps.json`**；`plan.md` 契约不动 | `plan.md` 散文无法机器解析；技能自检契约禁止新增 `##` 小节，改文档契约代价高。落盘机器产物是本仓库既有模式（`discussion.md` / `knowledge.json` / `backfill-issue.json`） |
| **D2** | 依赖存储位置 | **只留 `deps.json`**（单一事实源），**不写入 `Task`** | 由提案人拍定。`deps.json` 在项目挂载时随 `plans` 批量读入内存（按 `planId` 缓存），在「生成待办后 / 追加完成后 / 手动刷新」三个点重读 → 运行时门禁是**零 I/O 的纯状态派生** |
| **D3** | 「已完成」判定 | 仅 `status === "done"` 算满足 | 共享工作区下「产物已可见」= 依赖满足的真实条件；用 git 记录做二次校验会因分支/base 差异产生脆弱误判。`failed`/`cancelled`/`interrupted` 一律**不放行** |
| **D4** | 等待态表示 | 新增 `TaskStatus = "waiting_deps"` | 「等待前置」用户可见且需独立操作（取消等待）；复用 `todo`+字段会变隐式状态、每个新 UI 都要特判；复用 `pending` 会落入 `isActiveTaskStatus`（`types.ts`）而卷入活跃任务恢复逻辑，有误启动 PTY 风险。**`waiting_deps` 不进 `isActiveTaskStatus`** |
| **D5** | 检查驱动机制 | 状态驱动 + 应用启动/项目挂载时全量重算（**零定时器**） | 依赖是否满足完全由 `tasks` 数组派生，比定时轮询更准（任务删除、改绑都能立刻反映）；符合仓库既有「Tauri 事件驱动异步状态更新」约定 |
| **D6** | 门禁强度 | 硬依赖 → 等待；前置异常时**可手动越过** | 前置失败往往需要人判断「重跑前置」还是「这个前提其实不影响我」——不该自动放行（等于白做依赖分析），也不该卡死 |
| **D7** | 默认并发 | 同项目**默认串行**（上限可配，默认 1） | 原始痛点的根治项：多个等待任务被同一前置同时解锁时，若一起放行就原样复现「同区域并发」。串行是统筹节「建议执行顺序」的忠实执行 |
| **D8** | 建议顺序承载 | `deps.json` 加 `executionOrder: string[]` | 把统筹节「建议执行顺序」落实成确认页初始顺序，顺带修掉「确认页初始顺序 = 勾选顺序」这个现存缺陷；比 `after` 弱化边更简单且信息不重复 |
| **D9** | 适用范围 | **仅方案链路**（`planId` 有值且有依赖的任务） | 与 D2 自洽；手工任务 / 直接执行待办 / 补录待办行为完全不变 |
| **D10** | 缺失/损坏处理 | `deps.json` 缺失或解析失败 = **视为无依赖** | 覆盖存量方案（本功能上线前创建）与 agent 未按契约产出的情况，避免门禁退化成「没有依赖文件就不让跑」的硬故障 |
| **D11** | 破环策略 | `dependsOn` 成环 → **环内边全部丢弃**并告警 | 不允许门禁死锁。用迭代式 Tarjan 只删强连通分量**内部**的边，环外正常依赖保留 |
| **D12** | 异常前置处理 | 前置 `failed`/`cancelled`/`interrupted`/被删除 → 等待任务**保持 `waiting_deps` + 标红 + 通知一次** + 提供「忽略依赖，仍然开始」/「取消等待」。**不自动放行、不静默等待** | 自动放行 = 白做依赖分析；静默等待 = 用户以为系统卡了 |

### 3.1 明确不在本期范围（已讨论，暂缓）

- **新议题并入已有方案（「追加」）**：讨论中途识别出多个硬问题——`plan.issues` 创建后不可变（生成待办只以它为来源，没有并入入口）、执行任务 prompt 是生成时冻结的内联快照（方案重写不会更新它）、且会引入「新议题成为已在跑议题前置」的反向依赖不可满足问题。**撤回本期结论，单独一期讨论。**
  > **2026-09-14 更新**：已按「单独一期」重启讨论，解法为**追加议题 = 新建子方案（`parentPlanId`）**，不改写主方案，从而绕开上述三个硬问题。详见 [`yunxiao-plan-board-and-lifecycle-v1.md`](./yunxiao-plan-board-and-lifecycle-v1.md)。该文档同时提出「方案看板」与「方案生命周期管理」，与本篇的依赖门禁互补。
  >
  > **对本文（依赖门禁）的连带影响**：追加议题的跨方案依赖改由讨论 agent 按议题自行分析（不依赖"主方案完成"），因此本文的 `deps.json` 契约需放宽——`dependsOn` 允许引用**祖先方案**的议题编号（现状是"本方案外编号一律丢弃"，见 `planDeps.ts` 的 `unknownDependency`）。这是本文 §3.1 之外、由看板方案引入的**唯一契约改动**；门禁判定 `evaluateTaskGate` 与定序 `topoSortPlanIssues` 无需改动。
- **文件级同区域冲突检测**（比对议题「预计改动文件」并对重叠告警）：需要当前不存在的元数据，属下一阶段增强。
- **任意任务手工依赖**：与 D2 冲突，需先推翻该决策。
- **补录议题自动继承来源任务为前置**：语义合理但属新增范围。

## 4. `deps.json` schema（草案）

与 `plan.md` 同目录：`.nezha/plans/<planId>/deps.json`

```json
{
  "version": 1,
  "issues": [
    { "serialNumber": "QHDK-29749", "dependsOn": [] },
    { "serialNumber": "QHDK-29750", "dependsOn": ["QHDK-29749"] }
  ],
  "executionOrder": ["QHDK-29749", "QHDK-29750"]
}
```

**字段语义**

- `issues[].serialNumber`：议题编号，必须与 `plan.md` 的 `## <编号> ` 节标题、`Task.yunxiaoSerialNumber` **同一字符串**。
- `issues[].dependsOn`：直接硬依赖编号数组（硬依赖语义 = **前置不完成能否开工**，答案是不能）。
- `executionOrder`：方案级建议执行顺序（确认页初始顺序 + 队列 tie-break 优先级）。

**校验规则**

| 情况 | 处理 |
|---|---|
| 引用**不在本方案内**的编号（`dependsOn` 越界） | 丢弃该条边 + `unknownDependency` 告警 |
| `issues[].serialNumber` 不在本方案内 | 丢弃该议题条目 + `unknownIssue` 告警 |
| 依赖自身 | 丢弃该边 + `selfDependency` 告警 |
| 成环 | 环内边全部丢弃 + `cycle` 告警（D11） |
| JSON 损坏 / 顶层非对象 / 字段类型错 | **宽容解析**，能读多少读多少 + `malformed` 告警；整体不可读则视为无依赖 |
| 文件缺失 / 空白 | 视为无依赖 + `missing` 告警 |
| `version` 存在且 ≠ 1 | 仅告警（允许旧代码读到告警而非静默按 v1 误读） |

> **宽容解析是刻意的**：文件由 agent 生成，严格校验一旦误判会把任务永久卡住；坏数据降级为「少拦一条边」+ `warnings`。

## 6. 验收标准（10 条）

1. 方案含 `A → B` 硬依赖时，A 未完成点 B 的开始 → B 进入 `waiting_deps`，Checklist 中 A 未打勾。
2. A 完成后 B **自动启动**；A 仍在运行时 B 处于队列等待，A 结束后才启动（默认串行）。
3. A 变为 `failed`/`cancelled`/`interrupted` → B 保持等待 + 标红 + 通知一次 + 出现「忽略依赖，仍然开始」。
4. 删除 A 任务 → B 的 Checklist 显示前置缺失并标异常，不静默永久等待。
5. **无依赖任务点开始 → 立即启动，行为与现状完全一致。**
6. `deps.json` 缺失 / JSON 损坏 / 存量方案（无该文件）→ 视为无依赖，任务正常启动。
7. 确认页增删改依赖：形成环被拒绝并提示；保存写回 `deps.json`；队列顺序按 `executionOrder`。
8. 看板、状态图标、项目活动指示器对 `waiting_deps` 均有正确呈现（任务**不消失**）。
9. 四个主题（dark / midnight / light / eyecare）下等待角标与 Checklist 可读。
10. `pnpm lint` / `pnpm test` / `pnpm build` 通过；新增解析与拓扑排序逻辑有单测覆盖（含环、越界编号、缺失文件）。

## 7. 风险与代价

- **新增 `TaskStatus` 值需清点全部分支**（约 10 处），漏改 `columnForStatus` 会让等待任务在看板消失（见 5.3）。
- **串行队列会拉长总耗时**：整链变为串行总和；在跑任务若长时间 `input_required` 等人，队列会阻塞——需在待办列表显式显示排队原因（「队列中：QHDK-29750 正在运行」）。
- **依赖在两个文件里表达**：`plan.md` 统筹节散文与 `deps.json` 结构化数据可能不一致；靠技能自检（同步重写）+ 确认页可视化人工复核兜住。
- **门禁判定完全依赖前端状态派生**：`deps.json` 解析失败即静默降级为无依赖。这是有意的可用性取舍，但需在确认页对「依赖为空」给出提示，避免用户误以为门禁生效。

## 8. 头号评论补充：同工作区并发编辑的「逻辑打架」风险

issue #85 第一条评论单独分析了并行改同区域代码的风险，结论：**会出现，且当前没有任何机制阻止。**

### 8.1 已核实事实

1. **方案待办共享同一工作区、无隔离**：生成的是普通 todo，不带 `worktreePath` / `batchId`。
2. **启动路径无并发守卫**：`invokeRunTask` 直接 spawn PTY，不检查同项目是否已有任务在跑——想启几个启几个，cwd 都是项目根。两个 agent 进程各自读写同一棵文件树，**没有文件锁、没有协调，同文件写入即后写覆盖先写，静默无报错**。
3. **隔离设施存在但本链路刻意不用**：`create_task_worktree` 可一任务一 worktree；分支批的设计本就是「一个批对应一个分支 + 一个 worktree，批内任务顺序共用」。但生成待办不建批——这是一处刻意的分叉。
4. **唯一现有防线是 prompt 请求**：`utils/plan.ts` 写了「当前工作区可能还承载其他议题任务的改动，只提交本议题相关的改动，不要夹带其他议题的修改」。三个弱点：约束的是**提交（夹带）而非编辑**；agent 无从知道对方改了什么；没有任何校验，纯靠自觉。

### 8.2 两类问题必须分开看，第二类更危险

| | 机械冲突 | **逻辑打架** |
|---|---|---|
| 形态 | 同文件同区域编辑，git 报冲突 | 两边改动都能干净应用、git **零冲突**，但语义互斥 |
| 例子 | — | A 改了函数契约（加参数/改返回），B 仍按旧契约调用；A 加了防御性判空，B 按旧认知把它「简化」掉；A 和 B 各写一份同类 helper；A 删了 B 刚开始用的符号 |
| 可检测性 | 可检测、可恢复 | **git 检测不到，任何 merge 工具都检测不到** |

**worktree 隔离也治不了第二类**——它只是把问题推迟到合并时暴露，那时两边都已建立在互不兼容的假设上。

### 8.3 防护手段分级（L1–L5）

| 层 | 手段 | 覆盖 | 评价 |
|---|---|---|---|
| **L1** | 同工作区同时只跑一个 agent | 机械冲突 + 并发的逻辑打架 | **治本**。已在 D7 默认值内，但**有缺口**：原设计只串行「自动接续」，用户手动点两个无依赖任务的 ▶、或用「忽略依赖仍开始」越过，仍会并发 → 守卫须放到**启动收口处** |
| **L2** | `deps.json` 硬依赖 | 方案里**已分析到**的顺序 | 已有；但漏判的依赖不受保护，不能只靠它 |
| **L3** | 触达集重叠即串行（任务声明预计改动文件，重叠就不同时跑） | 未声明依赖但改同区域的组合 | 原提案按结论缓做；代价：agent 的预计不一定准，属近似 |
| **L4** | **前置产物注入**：任务自动接续时，把前置的**实际改动**（`git diff` / 变更文件 / 相关 commit）注入其 prompt，并要求先读前置改动再动手 | 串行下残留的逻辑打架 | **最便宜、最对症**。当前执行 prompt 只带方案的「设计意图」，**不带前置「实际改了什么」**——这正是串行场景下逻辑打架的温床 |
| L4' | 收尾范围校验：任务结束比对 `git diff --name-only` 与议题声明范围，越界告警 | 夹带 / 误伤他议题 | 可复用批次功能既有的「commit 门禁」雏形 |
| **L5** | 一任务一 worktree（物理隔离） | 机械冲突 | 治不了逻辑打架；且方案待办「跑在当前工作区」是刻意设计（现场响应类改动需要用户本地实时状态），加 worktree 要引入合并回主工作区的额外步骤。建议做成**可选**（「这批待办按批启动」），不作默认 |

### 8.4 结论（2026-09-14 已拍板）

- **纳入本期（必做）**：**L1 补手动启动缺口**（启动收口处的工作区级串行守卫）+ **L4 前置产物注入**。
  - L1 落在唯一启动收口点 `handleRunTodoTask`（`App.tsx`）：除依赖门禁外，再加"同项目已有活跃任务则排队"的守卫，堵住"用户手动点两个无依赖任务的 ▶"与"用『忽略依赖仍开始』越过"两条并发路径。
  - L4 落在任务自动接续时：把前置的**实际改动**（`git diff` / 变更文件 / 相关 commit）注入后继任务 prompt，并要求先读前置改动再动手——这是串行下「逻辑打架」最主要的温床。
- **建议纳入**：L3 触达集重叠串行。
- **保持可选**：L5 worktree 隔离。
- L4' 收尾范围校验作为下一期增强（需先定义「议题声明范围」从哪来）。

> 落地批次：L1+L4 属**第二阶段**（依赖门禁与串行调度），见看板方案 §7 的 E2/P1 决策。
