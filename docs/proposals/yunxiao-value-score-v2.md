# 提案：价值评分 v2 — 面向 Agent 研发绩效的评分规则重构

> 状态：提案。改动载体是 SkillHub 技能 `issue-value-scoring`（SKILL.md 评分模型 + 输出格式），
> Nezha 主仓的解析代码（`value_score.rs` / `yunxiao.ts`）只做小步兼容扩展。

## 1. 背景与动机

价值评分服务于**研发月度绩效**：系统按「处理议题数量 + 价值评分总和」反映一个研发当月的产出。

工作模式已变：**修改由 Agent 执行，研发的投入是「敲定方案 + 验收」**。当前评分规则把
「技术/修复成本」作为除数（Req）或不计分（Bug），直接后果是：

- **评分奖励的是"议题本身便宜"，而不是"研发处理得好"**——同样的业务价值，改动越小分越高；
  30 分钟的一行开关能拿满分 125，跨模块 3 天的硬骨头最多和它持平。
- **复杂议题（方案难敲定、验收链路长）被系统性压低**——恰恰是这类议题上研发的方案
  设计与验收保障投入最大、承担的风险最高。
- 月度汇总时「挑软柿子」策略收益最高，与绩效导向背道而驰。

## 2. 实证数据（2026-10-14 拉取，24 个已回写议题）

Req（10 个）：均值 59.6，中位 48，2 个满分 125。
Bug（14 个）：均值 39.3，中位 33.75，1 个满分 125。

| 反推（按 v1 公式） | "1 行开关" 类议题 | "跨模块多日" 类议题 |
|---|---|---|
| 业务价值 4×影响 4×紧急 4 | 64（S） | 8.5（B） |
| 业务价值 5×影响 5×紧急 5 | **125（S）** | 21（A） |

业务影响完全相同的两个议题，仅因 Agent 改动量不同，分差 **7-15 倍**。
而按工时字段对照：指数与实际投入基本无关（125 分的三个议题实际工时 1/3/1 小时，
48 分的手麻数据流转工时 2，30 分的预交金接口工时 3 但方案复杂度最高）。

结构性问题清单：

1. **成本当除数 = 惩罚难题**（Req）。w=6-成本分，难题成本分 1-2 → w=4-5，指数被除到很低。
2. **Bug 完全不计研发侧质量**（修复成本不进公式），复杂修复无任何加分路径。
3. **"数量 × 总分"口径下，低成本议题重复刷分**——一行开关修 10 个 ≫ 啃一个跨模块难题。
4. **讨论/验收价值不可见**——方案折衷、验证方案设计、验收把关这些研发实际工作无对应维度。
5. 输出格式漂移（无日期版/「价值评判」标题/「核心指数 50 = 价值4×机会5」旧版公式共存），
   解析已兜住，但说明字段约束弱。

## 3. v2 评分模型（绩效导向）

核心转变：**从"议题值多少"转向"研发把这件事处理得有多好"**。
业务价值保留（反映议题本身的分量），成本反转为"交付难度"计分项，新增"方案与验证质量"维度。

### 3.1 Req（7 维）

| 维度 | 1 分 | 3 分 | 5 分 |
|------|------|------|------|
| 业务价值 | 个别用户偏好 | 单科室流程优化 | 直接增收 / 显著降本 |
| 用户影响 | 个别人偶尔用 | 单科室全员每日用 | 全院多角色每日高频 |
| 紧急度 | 无时间要求 | 本季度内 | 硬性窗口（医保切换/评审/上报截止） |
| **交付复杂度**（原技术成本反转） | 一行配置/单点小改（半天内） | 单模块多文件（1-3 天） | 跨模块/跨工程/架构级（≥3 天） |
| **方案质量**（新增） | 直接照做无设计 | 常规方案 | 多方案权衡/兼容存量/绕开风险 |
| **验证与验收价值**（新增） | 走查即可 | 常规回归 | 需设计专项验证/多环境/数据核对 |
| 依赖关系 | 完全独立 | 被 1 个事项依赖 | 阻塞多个议题或上线计划 |

计算（**只乘不加权，成本从除数改为乘数**）：

- **核心指数 = 业务价值 × 用户影响 × 紧急度 × 交付复杂度系数**，
  系数 = 0.4 + 0.2 × 交付复杂度分（1→0.6，3→1.0，5→1.4），范围约 1.2-245；
- **修正项 = 方案质量 + 验证与验收价值 + 依赖关系**（3-15），≥12 升半档、≤5 降半档；
- 定档阈值随指数范围整体上调：≥36 → S；14-36 → A；5-14 → B；<5 → C（修正同 v1 封顶封底）。

### 3.2 Bug（8 维 → 7 维）

| 维度 | 变化 |
|------|------|
| 严重程度 / 发生频率 / 影响范围 / 业务影响 / 数据风险 / 安全合规 | 保持 v1 |
| 修复成本 | **不进公式、不废弃**：仅作排期参考列出（v1 精神保留） |
| **诊断与验证难度**（新增） | 1=现成结论照改；3=常规排查定位；5=跨系统取证/复杂回归设计 |

计算：

- 优先指数公式不变：严重 × 频率 × 范围 × 折减系数（范围 0.4-125）；
- **研发贡献系数 = 0.85 + 0.05 × 诊断与验证难度分**（1→0.9，3→1.0，5→1.1）；
- **绩效指数 = 优先指数 × 研发贡献系数**（进议题字段与月度汇总）；
- 定级沿用 P0-P3（反映缺陷本身优先级，供排期；绩效用绩效指数）。

### 3.3 绩效映射（月度汇总）

- 研发月度产出 = Σ(处理议题的绩效指数) + 议题数量；
- 复杂议题天然高分：交付复杂度 5 的 Req 即使业务一般（3×3×3），指数 37.8 ≈ 已达 S 档；
  一行开关类上限被压到 126×0.6=75.6 区间以下（乘系数后实际 ≈ 业务分 × 系数）。

## 4. 改动范围

| 文件 | 改动 |
|------|------|
| SkillHub `issue-value-scoring/SKILL.md` | 评分模型、输出格式（新增两行维度与系数推导）、fixtures 同步 |
| `src-tauri/src/value_score.rs` | `parse_value_score_index` 兼容「绩效指数」行（向后兼容旧「核心/优先指数」） |
| `src/utils/yunxiao.ts` | `parseValueScoreIndex` 同步兼容 |

解析保持「取标签后第一个数字」，新旧格式并存不破坏回写链路。

## 5. 迁移与验证

- 技能 fixtures 增加 v2 格式的 Req/Bug 各一个基准；
- 解析单测：新格式「绩效指数」、旧格式「核心/优先指数」、混合标题三种都能取到值；
- 用本次拉取的 24 条真实评论回代 v2 公式做 diff 试算，确认复杂议题分数上移、
  简单议题不失真后再切换。

## 6. 回代试算结果（2026-10-14，18/24 条评论维度齐全）

Req（v1 除法 → v2 乘法，未计新增修正项的保守口径）：

| 议题 | v1 指数 | v2 指数 | 说明 |
|------|--------|--------|------|
| QHDK-30760 自助机医保结算个账适配 | 125 | 175 | 政策窗口刚需，v2 下高分更合理 |
| QHDK-30724 挂号医保信息弹窗 | 40 | 96 | 单科室需求，v1 被压到 A+，v2 回归 S |
| **QHDK-30563 预交金退费回写接口** | **30（B+）** | **72** | 资金对账 + 阻塞上线 + 双环境验收，v1 严重低估 |
| QHDK-30672 儿童体检打印参数 | 36 | 50.4 | 小改进，小幅上移不失真 |
| QHDK-30701 挂号单数据源 | 30 | 42 | 低复杂度需求，温和上移 |

Bug（优先指数 × 贡献系数，诊断难度默认 3 保守估计）：

| 议题 | v1 优先指数 | v2 绩效指数 | 说明 |
|------|-----------|-----------|------|
| QHDK-30656 网上采购价医保支付报错 | 50 | 55 | 跨端取证（诊断 5），上浮 10% |
| QHDK-30683 个检登记读卡异常 | 7.2 | 7.9 | 可绕行小缺陷，仍 P3，排序不变 |
| 其余常规修复 | 不变 | 不变 | 诊断难度 3 → 系数 1.0 |

结论：**Req 复杂议题（方案/验收重的）最大上移 +140%，简单议题温和上移且不改变高价值
议题的领先地位；Bug 复杂取证修复 +10%，排序不受扰**。S 档阈值上调（≥36）后，
v1 里 6 个 S 档中仅业务影响确属顶格的保留 S，避免全员 S 导致月度区分度归零。
