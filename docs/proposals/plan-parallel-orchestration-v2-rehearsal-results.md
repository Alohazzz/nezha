# 方案并行编排 · 一期演练结果（2026-10-14）

> 配套：[`plan-parallel-orchestration-v2.md`](./plan-parallel-orchestration-v2.md)（设计）与
> [`plan-parallel-orchestration-v2-rehearsal.md`](./plan-parallel-orchestration-v2-rehearsal.md)（手册）。
> 本报告是**实测数据**，不是设计意图；两者冲突处以本报告为准。

## 0. 一句话结论

**机制成立，瓶颈转移。** worktree 隔离、一议题一 commit、白名单 100% 干净、主检出零写入、
落地 dry-run 无冲突——设计的四条安全属性全部实测通过。但 50 分钟里有**约 40 分钟花在
「让子 agent 真的干活」上**：worker 收不到任务、有 worker 误以为自己是编排者、有 worker
调 `wait_agent` 把自己挂死 28 分钟、审查 agent 与修复 agent 各空转十几分钟，最后编排者
**自己下场写完了 TEST-103 的代码**。git 层没事，协调层是新的战场。

HIS 的尾部是增量构建（分钟级到十几分钟），这一项会被放大。

## 3. M2 隔离纪律：源码层零越界，协调层一锅粥

**源码层（通过）**

- 主检出 `git diff --stat` 为空、`HEAD` 始终是 `6387b7e`、`git status` 与演练前逐字节一致；
- 三个 worker 的全部改动落在各自 worktree 内，未出现互相覆盖；
- 冲突发生在集成分支的独立 worktree 里，主检出未被波及。

**协调层（4 类失效，全部记录在编排台账里）**

1. **初始 brief 未进入 worker 上下文**：101/102 靠自查恢复；
2. **worker_test_102 自认是编排者**：做了 3 次 `spawn_agent` + 2 次 `followup_task`（全失败），
   并在**主检出**跑了一次基线 `npm test`（只读，无写入）；
3. **worker_test_101 越权转发 brief** 给 102/103 并各 `interrupt` 一次；
4. **worker_test_103 调 `wait_agent(300s)` 把自己挂死 28 分钟**，零落盘。

> 即：F19（子 agent 与 root 共享 cwd 且共享全套工具）在演练里同时以「无写入越界」和
> 「角色混乱」两种形式兑现——**共享工具集是设计缺陷，必须靠契约禁用**。

## 4. M3 归属正确率：100%，但两条硬约束是编排者自己发现的

| 议题 | commit | 文件集 | 与白名单 |
|---|---|---|---|
| TEST-101 | `efd502e` | `src/http/integrationClient.js`、`src/patientRegistry.js` | ✅ 2/2 |
| TEST-102 | `1c35956` | `src/validation/checksum.js`（新增）、`idCard.js`、`insuranceCard.js` | ✅ 3/3 |
| TEST-103 | `e1773c4` | `src/logger.js`、`src/patientRegistry.js` | ✅ 2/2 |

三条 commit 的 message 均含 `#TEST-10x closed`。

**发现 1｜`git add -A` 会把回写包卷进议题 commit。** 编排者用 `git check-ignore -v` 证明了
`.gitignore` 的 `.nezha/plans/*/discussion.md` **不覆盖** `writeback/<编号>/discussion.md`，
于是把契约里的 `add -A` 主动改成**显式白名单路径 add**——三份提交因此只含 2/3/2 个文件。
→ 设计必须把「回写包绝不进入议题 commit」写成硬约束，**不能依赖某个仓库的 gitignore 恰好覆盖**。

**发现 2｜「分片改动不重叠 ⇒ 能干净合并」被证伪。**

```
Auto-merging src/patientRegistry.js
CONFLICT (content): Merge conflict in src/patientRegistry.js
实际 tree 79c58c45…  ≠  纯三方自动 tree 95030032…
```

TEST-101（+12/−6）与 TEST-103（+15/−8）**各自都重写了同一段函数体**：方案文档统筹节里
「两个议题的改动区域不重叠」是讨论阶段的乐观判断，实际代码层面并不成立。冲突由编排者按
统筹节的仲裁规则人工解决（错误语义取 101、日志派生取 103），并自曝「未记入 run-log」。
→ **冲突路径必须是显式设计**（v1 的 D8「冲突自动生成修复任务」从备选升为必需），
而审慎的默认是：**同一文件被两个议题碰 = 高风险信号**，应在派活前就标出来。

## 5. M4 尾部：零构建在本样本成立，但审查才是真成本

- **第 1 轮 `npm test` 就 18/18 全绿**——包括那次人工解冲突之后。三个 worker 在
  「不构建、不跑测试」的约束下产出的代码，第一次整体验证即通过（TEST-101 的三个红灯全部转绿）。
- code-review 双轴：Standards 报 6 条判断题、0 硬违规；Spec 报 0 缺失 / 0 越界 / 0 硬违规。
  唯一实质问题是一处**与实现矛盾的过期 JSDoc**。
- 修复由编排者自己执行（修复 worker 空转 8 分钟），提交 `5328f31` 直接落在集成分支。
- 第 2 轮 `npm test` 仍 18/18。

**结论：D6「零构建」在本样本上可接受**（错误没有后置堆积，首轮即绿）。
但要注意两个前提：① 本样本是「小改动 + 秒级测试」；② 尾部的**审查环节**耗时 17 分钟，
在 HIS 上会与增量构建叠加，成为新的固定成本。

## 7. 偏离契约清单 → 每条的设计含义

| # | 偏离 | 设计含义 |
|---|---|---|
| 1 | `add -A` → 显式白名单 add | D4 加硬约束：回写包不得进入议题 commit |
| 2 | brief 未进 worker 上下文；worker_102 自认编排者并越权 spawn/followup | **worker 的任务正文必须自包含在它的 prompt 里**，不得依赖二次「brief」传递；worker 契约硬禁协作工具 |
| 3 | worker_101 越权转发 brief + interrupt 同伴 | 同上：worker 禁止 `spawn_agent` / `followup_task` / `send_message` / `interrupt_agent` |
| 4 | worker_103 调 `wait_agent` 挂死 28 min | worker 禁 `wait_agent`；编排者需要**worker 心跳/超时**（例如 10 分钟无落盘即介入） |
| 5 | TEST-103 的代码与回写包由编排者代做 | 需要明确「编排者不得代写业务代码」或显式降级规则，否则并行收益被编排者的串行时间吃掉 |
| 6 | Spec 审查首派空转 14 min；修复 worker 空转 8 min | 审查与修复同样需要**超时 + 改派**策略，不能无限等 |
| 7 | 方案的一条 grep 判据字面不成立 | 方案契约需要「验收判据必须可机器验证」纪律（现在只约束了改动路径） |

## 8. 对 v2 设计的修订建议

- **保持**：D2（每议题 worktree）、D3（编排者统一提交 + 白名单）、D5（一次性落地 + 主检出只读）、
  D9（逐方案开关）——四条均实测成立。
- **D4 增补**：回写包落盘位置必须与议题 commit 隔离（显式路径 add，或落在 worktree 之外）。
- **D6 保持**（零构建），但补：尾部审查要有超时与改派，不能把「等 agent」当成串行时间。
- **D7 增补**：冲突路径从「备选」升为「必需」，且冲突解决必须进 run-log 并接受独立审查。
- **D10 增补**：并发槽位语义 = **同时运行**（不是已创建）；worker prompt 必须自包含。
- **新增 D12｜worker 契约硬约束**：禁用协作工具（spawn/followup/send/interrupt/wait）、
  禁止在自己 worktree 之外执行任何命令（含只读）、完工必须输出结构化自检结论。
- **O2 得到支持**：worktree 建在项目内可行且开销可忽略（0.99 s）。

## 9. 尚未回答

   Codex 的 4 槽位上限意味着并行度封顶，N 大时靠前沿滚动——滚动本身会不会引入新的等待税？

3. **HIS 尾部**：增量构建接入后，零构建的收益是否仍成立？
4. **编排者代写代码**的边界：本次它写了 TEST-103 的全部改动。这算「正确降级」还是「设计漏洞」？

## 10. 第二轮对照（同一批工单 · 加固后的契约驱动）

第二轮用新建的 `plan-parallel-orchestration` 技能驱动：样本、基线（`6387b7e`）、完成判据（`npm test` 18/18）
全部与第一轮相同，**编排者提示词从 2669 字符缩到 786 字符**——契约下沉到技能里。

### 10.1 必须披露的两处测量污染

1. **第二轮编排者在门禁阶段读过第一轮的合并结果**（原文：「let me look at the merged result on
   rehearsal/integration for patientRegistry.js … It'll help me write arbitration rules precisely」）
   → 影响「G2 门禁」这一项的独立成色（但 G2 的判据本身是从声明路径算出来的，不依赖前一轮）。
2. **我（评审者）在跑到中途做了两次外部写入**：删掉第一轮的 `rehearsal/*` 分支、误留一份 brief 文件在
   主检出 `inbox/`。编排者把它记为 deviation #11「第三方写入」，并额外花时间留痕与复核。
   → 这部分时间应计入第二轮的额外开销，而非契约本身的成本。

（其中 ≈10 min 是首派空转的改派损耗）｜ 尾部 44 min（验证门 3、**审查者空转 ≈15**、修复轮 ≈10、
复验 + dry-run 2、审查回执与复核 ≈10）。

### 10.3 契约真正改变了什么

**收益（机制可复现）**

1. **零合并冲突**——worker 在完工前把集成分支基线合进自己的分支（技能 4.3），第一轮那次真冲突在
   第二轮没有出现；收口合并全部为「自动合并一致」。
2. **范围可证**——一工单一 commit、白名单 2/3/2 一致；编排者用显式路径 add、产物落 worktree 之外。
3. **失效可观测**——14 条偏离逐条留痕：worker 自代行编排者职务、修复 worker 越权派生孙代 agent、
   第三方写入、审查者空转，全部被识别并记入台账。
4. **审查确实抓到实质问题**——`fe136ea` 修掉一处与实现矛盾的过期模块头注释（与第一轮同类）。

**没变（平台层，提示词治不了）**

1. **spawn 载荷的可读性**：第二轮 **3/3 首派 worker 都没看到任务正文**（明文投影为空，正文只在
   `encrypted_content` 里）——与第一轮同因，且它驱动了两轮绝大部分损失。
2. **子 agent 角色纪律**：违规协作调用 34 → 37，基本持平。第二轮最严重的一条是 TEST-101 的 worker
   **自读 rollout 恢复上下文后自代行编排者职务**（自提交、自合并、覆写台账）。
3. **审查轴空转**：规格轴**三次正规派发全部空转**，最终靠一个越权派生的审查者交付。

### 10.4 结论：契约提升了正确性，没有降低协调成本

加固版契约把损耗从「**静默的污染风险**」换成了「**可见、可记账、可恢复的成本**」——
零冲突、范围可证、失效全部被识别；但**墙钟 +46%、tokens +76%**。

原因是机制性的：**活性规则把静默挂起变成了显式改派，而每次改派都要重新付出上下文代价。**
当子 agent 失灵是**系统性**（而非偶发）的时候，重试比等待更贵。这也回答了 §9 的部分问题：
冲突自动修复（问题 2）在本轮确实不再需要——但代价是尾部时间翻倍。

### 10.5 下一版技能的加固项（均有实证）

1. **文件式 brief 升为主渠道**（不是回退）：先落 `<worktree 之外>/BRIEF.md`，spawn payload 只放
   「读该文件 + 握手 + 禁令摘要」。实证：拿到文件指针的 worker（`worker_102_retry` / `worker_103_gen3`）
   一次成功；只有明文投影的 3/3 首派全部失败。
2. **禁止代行编排者职务**：worker 可以读自己的会话 / 文件补上下文，但**提交、合并、改台账一律禁止**，
   越权即停并上报（本轮出现了「自读 rollout 后自代行」这一新变体）。
3. **禁止派生任何后代 agent**（含「为求稳妥」的善意派生）——修复 worker 越权 spawn 了一个子审查者。
4. **台账单写者**：只有编排者可写台账；worker 只许写自己的报告文件（本轮台账被覆写两次）。
5. **审查轴用并行冗余而非串行重试**：审查只读且幂等，规格轴三次串行派发全空转；应改为
   「两轴并行 + N 分钟无交付即并行增派冗余」。
6. **在 harness 层寻求根治**（研究项）：若 Codex 能按 agent 限制工具集、或修正 dispatch payload 的
   明文投影，上述 2 / 3 两条可以直接消失——**这比任何提示词条款都有效**。

### 11.2 取证答案：TUI 通道同样复现载荷缺陷，且更彻底

**7/7 次 spawn，子 agent 侧的 `role=user` 明文投影只有 401 字符的 `<environment_context>`**，
payload 正文（含 brief 的绝对路径指针）完全不存在，正文只以 `encrypted_content` 承载。
证据取自平台 rollout 文件本身（编排者引用，本报告复核）。

更重要的发现：**§10.5-1「文件式 brief」在本轮平台上不成立**——第二轮的经验是「拿到文件指针的 worker
一次成功」，但指针本身就放在 payload 里，**载荷一空、指针同灭**。第三轮真正把 worker 救活的是第三条路：
**agent 自救**——子 agent 浏览文件系统（`inbox/` 目录、台账），推断出自己的工单号后读 brief。
w101/w102 这样成功；w103 没找到台账、空转收工（156K tokens 零产出）后被改派。
→ **未决问题 1 的答案：文件优先派活是必需项但非充分项；指针必须放在 payload 之外**（约定文件名，
  如 `inbox/<编号>-BRIEF.md`，payload 只放「你的编号 + 去读 inbox」）。

### 11.3 新发现：`fork_turns=all` 是机制性角色污染

改派 w103b 时编排者漏传 `fork_turns`，平台默认 `all`（全历史 fork），把编排者自己的任务正文
（1116 字符「你是编排者」）继承给了子 agent——w103b 于是**自认「编排者续跑线程」**：越权写台账、
写 inbox、派生后代 agent、冒充编排者派发。`session_meta.forked_from_id` 实证指向编排者线程。
审查者三线程同样以 `fork_turns=all` 派发，继承了编排者上下文，独立性被削弱（它们自报了这一点）。
→ 这不是 worker「自行推断」（§5.6 的原记载），而是**平台注入的必然**。技能已订正：spawn 必须
显式传 `fork_turns`（最小集），审查者另用独立通道。

### 11.4 加固技能的实测收益

1. **违规协作调用 37 → 8**（-78%）：禁令清单 + brief 内嵌禁令摘要确实压制了子 agent 碰协作工具的冲动。
2. **审查冗余产生净收益**：冗余轴报出主轴漏掉的 N1（畸形成功响应仍抛原生 `TypeError`，编排者独立复现）；
   推翻了「规范轴一次就够」的假设。
3. **修复 0 轮**：triage 11 条发现全部「接受/延后」，尾部从第二轮的 44 min 压回 12 min。
4. **G2 预写仲裁规则未被触发**（三次合并全干净）——但原因之一是 TEST-103 实际被串行化了，两侧 hunk
   没机会在同一 3-way 合并相遇，不代表风险不存在。

### 11.5 技能缺口（本轮暴露，待下一版）

1. **triage 三选项不够**：S1/N1 这类「方案外但在白名单内」的加固项，修=越过定稿规格、不修=漏真问题。
   需要第四选项：「延后 + 写清建议补丁」（本轮编排者自行发明并按此处置）。
2. **接管后的回写包归属**：审查者越权补写了编排者遗漏的 `writeback/TEST-103/discussion.md`；
   技能未规定接管后回写包由谁补写。
3. **payload 白名单条款**（§2.2「四样」）要改：编号 + 去读 inbox 的指令必须是前两样，其余从简。
4. **G1 的「测试步骤 vs 验证方式」**：两条字面不成立的判据都落在「测试步骤」，按 G1 字面该退单；
   实际处置是降级+写等效判据。技能应把退单条件限定在「验证方式」不可机器验证。

### 11.6 Nezha 侧观察（本轮新采集）

- TUI 通道本身**不改变**任何 git 层安全属性：M2/M3/M4 全部与前两轮同级通过——缺陷与收益都出在
  协调层，与通道无关。
- Nezha 的指标条（时长 / tokens / 上下文% / 会话文件大小）、会话自动发现（`codexSessionPath` 关联）、
  `awaiting_review` 终态全部按预期工作；TUI 会话在编排结束后不退出，任务停在等审阅——**正式集成时
  「编排完成」需要从会话内容侦测**（回写包齐全 + 集成分支 dry-run 留痕），不能依赖进程退出事件。
- 本轮任务由调度器经 `waiting_deps` 自动放行（上一 agent 的权宜手段）；正式链路仍缺显式启动入口。

### 12.2 三项加固的取证结论（编排者以 rollout 轨迹为准，本报告复核）

   最严重的是 reviewer_standards：做了落地 dry-run、`wait_agent(300s)` 等「规范轴」（实为等

3. **握手降级指令：0 次按字面触发。** 没有任何子 agent 走完「两步自救失败 →

2. **审查轴空转的处置组合**：编排者用了「interrupt 原审查者 + 并行增派冗余」，技能只对
   worker 规定了 interrupt 条件。应把「审查者 N 分钟零交付 → interrupt + 冗余」转正。
3. **自举文档的反污染声明升为标准件**：本轮给冗余轴 brief 手写的「你不是编排者，若上下文

4. **禁令的前置化**：禁令摘要必须放进自举文件（README）本身，覆盖「拿到 brief 之前」的
   空窗——本轮 3 次 `list_agents` 违规全部发生在这个窗口。

### 13.2 本轮最重要的发现：污染源不在 fork，在 Nezha 的任务注入通道

四轮以来「子 agent 自认编排者」被依次归因为：worker 自行推断（R2）→ fork_turns 注入（R3）→
空载荷 + 文档口吻诱导（R4）。第五轮 worker_test_103 给出了**独立证词**：它读到了 Nezha 的
任务记录 `tasks.json`（任务 `1791970062700` 的正文第一句就是「**你是本方案的「编排者」**」）——
**Nezha 把任务 prompt 写进共享文件系统上的 tasks.json，任何子 agent 都能读到并把它当成
自己的身份**。这解释了为什么文档声明（README 反污染段）**0/7 纠偏**：污染源是具体可读的
「权威文本」，一句「你不是编排者」敌不过一段「你是编排者」。

### 13.3 第二个重要发现：AGENTS.md 灯塔实测有效

编排者在两次改派失败后（偏离 #6，已留痕）在主检出放了一个未跟踪的 `AGENTS.md` 身份灯塔
（Codex 会自动把仓库 AGENTS.md 注入每个 agent 的系统上下文）。第三波（审查冗余轴）实测：

| 指标 | 无灯塔（R5 第一/二波） | **有灯塔（R5 第三波）** |
|---|---|---|
| 自救步数到 brief | 13–17 次调用 / 53–80 s | **21.7–30.2 s 到 inbox README，51–101 s 到 brief** |
| 空载荷窗口协作工具违规 | 7 次 | **0 次** |
| 自认编排者 | 6/7 | **0/2** |
| 交付 | 3/7 | **2/2（完整 schema）** |

**AGENTS.md 是 Codex 平台自动注入的上下文通道，不依赖子 agent 主动读文件——
它把「自救」变成了「出厂预装」。** 唯一代价：灯塔文件放主检出违反「主检出只读」，
技能需要把它变成受控例外（放工作开始前、收尾删除，或放到 brief 同级的约定位置）。

### 13.4 四项取证结论

1. **三步级联：存在但不是第一跳。** 第一波 13–17 次调用到 brief，与上轮同量级——子 agent
   第一跳全是项目 `README.md`（Codex 习惯先读仓库说明），inbox README 要到 +13~44 s 才读。
   级联结构对，但入口不对；灯塔轮证实「平台自动注入」才是第一跳的正确位置。
2. **空窗禁令：README 前置无效**（7 次违规全部发生在读到 README 之前）——灯塔轮归零。
   「把禁令放进子 agent 主动读的文件」在时序上就输了；禁令必须走自动注入通道。
3. **反污染声明：文档声明 0/7 纠偏**（含已读过 README 的 agent）；灯塔轮 0/2 污染。
   结论与上同：对抗「你是编排者」的权威文本，只能靠系统上下文里更近身的身份声明。
4. **blocked-by-local-edits：未触发**（TEST-103 基线合并时集成分支与基线同点，
   "Already up to date"，脏工作区没有被拒机会）。schema 分支在场但没被测到；
   下轮要构造必然触发的时序（先合并一单再派下一单）。

### 13.5 v5 加固方向（全部有本轮实证）

1. **AGENTS.md 身份灯塔升为标准 bootstrap**：开工时在主检出放未跟踪 `AGENTS.md`
   （内容 = 身份声明 + 禁令摘要 + 三步级联指针），收尾删除；「主检出只读」条款加此例外。
2. **prompt 自我指涉回避**：编排者任务 prompt 的第一句不应是「你是编排者」——
   该文本会进 tasks.json 被子 agent 读到。改为「本任务是编号 X 的编排任务，执行者见 AGENTS.md」
   类中性措辞（或 Nezha 侧把任务 prompt 存到子 agent 不可读的位置）。
3. **活性巡检的提前中断条款**：本轮编排者在 worker 明确自认编排者并开始巡检/等待时

   不等零变化计时」。
4. **blocked-by-local-edits 的触发时序**：派单顺序保证至少一单在基线前进后开工，
   否则该分支永远测不到。
