## 1. 现状盘点（代码事实，先对齐）

### 1.1 方案没有聚合视图

现有与方案相关的 UI 只有三处，全部是**单方案 / 单任务**视角：

| 组件 | 视角 | 入口 |
|---|---|---|
| `PlanLaunchDialog` | 发起讨论（选议题 → 发起） | 云效视图 / 欢迎页 |
| `PlanPreviewPanel` | 预览单个方案的 `plan.md` + 图片 | 任务详情 / 云效视图 |
| `PlanTaskView` | 单个方案议题任务（关联方案条） | 任务选中时 |

**没有任何地方回答这组问题**：这个项目现在有几个方案？各自到哪一步了？方案的 N 个议题任务各自什么状态？哪些在等依赖？——这些信息目前散落在任务列表里，用户得自己脑补聚合。

### 1.2 生命周期是残缺的（核心痛点）

`src/types.ts` 定义了 `PlanStatus = "draft" | "finalized" | "executing" | "completed" | "cancelled"`，但全仓库搜索后的事实是：

- **`completed` 没有任何赋值点，永远不可达。** 方案一旦 `executing`，即使所有议题任务都 `done`，方案状态仍停在 `executing`，永远不会收敛。
- **`cancelled` 不是状态转移，而是删除。** `handleCancelYunxiaoPlan` 调 `delete_yunxiao_plan`，把方案记录从 `plans.json` 移除并清掉 `.nezha/plans/<planId>/` 目录。所以没有「已取消但可查」的归档态。
- 实际可达的状态转移只有两条：`draft → finalized`（讨论任务 done 时，`App.tsx` 的 effect）、`finalized → executing`（生成待办时）。

**结论**：方案实际上只有「讨论中 / 已定稿 / 执行中 / 被删除」四种可见形态，缺「已完成 / 已归档 / 已取消」的收敛与留存。

### 1.3 方案与任务 / 议题的关联

- `Task.planId` —— 任务归属方案；讨论任务另带 `yunxiaoPlanDiscussion: true`（定稿后退场）。
- `Task.yunxiaoWorkitemId` / `yunxiaoSerialNumber` —— 任务 ↔ 云效议题。
- `Plan.issues: PlanIssue[]` —— 方案快照的议题清单（**创建后不可变**；生成待办只以它为来源）。
- `collectOccupiedYunxiaoWorkitemIds`（`src/utils/yunxiao.ts`）—— 一个议题只能被**一个**存活方案或任务占用；方案被删除后其议题释放，可重新导入。

## 2. 目标愿景

把「方案」提升为**一等公民**，而不只是任务的附属：

1. **方案看板**：以方案为中心的聚合视图，一眼看到本项目所有方案的状态、进度、依赖。
2. **生命周期管理**：方案从讨论 → 定稿 → 执行 → 完成 / 取消 / 归档，全流程有明确状态与留存，不再「要么在跑要么消失」。
3. **看板内追加议题**：方案定稿后仍能继续扩展，且**不破坏**已定稿内容与在跑任务。
4. **进度与依赖可见**：看板上直接看到每个议题任务的进度、前置依赖是否满足、被什么阻塞。

## 3. 方案生命周期重新定义

### 3.1 现有 vs 建议

| 阶段 | 现状 | 建议 |
|---|---|---|
| 讨论中 | `draft` ✅ | `draft`（保留） |
| 已定稿 | `finalized` ✅ | `finalized`（保留） |
| 执行中 | `executing` ✅ | `executing`（保留） |
| **已完成** | ❌ 不可达 | **新增可达，且由使用者手动标记**（决策 M1，见 §3.3）：方案卡片的「标记完成」按钮置 `completed`。**不做自动收敛**——「方案是否算完成」由人判断（可能还有验收、手动补做、跨方案收尾等任务状态表达不了的事） |
| **已取消** | 实为「删除记录」 | 建议区分：**`cancelled` 作为留存状态**（保留记录与目录，可查看/可重开）；**删除**仍是显式操作（现 `delete_yunxiao_plan` 保留给「草稿阶段取消」与「确认删除」） |
| **已归档** | — | **新增「归档」动作**（AR1）：手动标记完成后，用户可将方案归档，从看板主视图移出到「已归档」区；可反归档。看板主视图只放活跃方案 |

### 3.2 建议的状态转移

```
draft ──[讨论任务 done]──▶ finalized ──[生成待办]──▶ executing
                                                          │
                              ┌───────────────────────────┼────────────────────┐
                              ▼                           ▼                     ▼
                    [使用者点「标记完成」]        存在 failed/cancelled     使用者显式取消/删除
                              │                    （看板标红提示）                │
                              ▼                           │                        ▼
                        completed                 仍 executing，等人处理       cancelled / 删除
                        （可再手动重开）
```

- **完成是手动动作**（决策 M1）：`executing` 的方案由使用者在看板卡片上点「标记完成」→ `completed`。**不自动收敛**——即使全部议题任务 `done` 也不自动转状态。
- **看板给提示、不代替决策**：当某方案的全部议题任务都 `done` 时，卡片显示「全部议题已完成，可标记完成」的**提示徽章**（派生，非状态），但不替用户转变状态。这样既不打扰「还在等验收/还差收尾」的方案，也不会让用户忘了收敛。
- **异常不阻塞标记**：存在 `failed`/`cancelled` 任务时同样允许手动标记完成——因为可能用户已接受部分失败、或改用别的方案处理了。本方案只做**提示**（标红），不做**阻断**。
- **可重开**：`completed` 的方案若发现仍有未了事项，允许「重开」回 `executing`（手动双向）。
- **子方案对主方案的影响**：见 §5.3 —— **跨方案依赖是逐议题的**：agent 分析出追加议题依赖主方案哪些具体议题，就只等那几个议题任务 `done`（决策 B2'）。方案生命周期（M1 手动标记）只决定看板列归属，**不参与依赖判定**。

### 3.3 本阶段已定决策（2026-09-14）

| 编号 | 决策 | 影响 |
|---|---|---|
| **A2** | **一次追加的一批议题合成一个子方案**（不是一议题一子方案） | 方案树"高"，每个追加动作对应一个子方案；子方案内部可含多议题，因而能表达追加议题**彼此之间**的依赖与顺序（A1 下单议题方案之间无法互相依赖） |

## 4. 方案看板设计

### 4.1 形态

**跨项目总览**（决策 S1）：按项目分组 × 生命周期列（`PlanStatus`），以方案为卡片单位——与任务看板 `KanbanView`（按项目分组 × 4 列）同构，但卡片粒度是方案。

```
┌─ 方案看板 ───────────────────────────────────────────── [搜索方案/项目] ── ✕ ┐
│                                                                               │
│  nezha-main                                            3 个方案 · 12 议题       │
│  ┌─ 讨论中 ─┐ ┌─ 已定稿 ─┐ ┌─ 执行中 ─────┐ ┌─ 已完成 ─┐ ┌─ 已取消 ─┐          │
│  │ (空)     │ │ QHDK-29… │ │ QHDK-29750…  │ │ QHDK-2…  │ │ QHDK-2…  │          │
│  │          │ │ 4 议题   │ │ ▓▓▓▓░ 4/5    │ │ 5 议题   │ │ 已取消   │          │
│  │          │ │          │ │ ⏳ 1 等待前置 │ │ 可标记完成 │ │          │          │
│  │          │ │          │ │              │ │ [归档]    │ │          │          │
│  └──────────┘ └──────────┘ └──────────────┘ └──────────┘ └──────────┘          │
│                                                                               │
│  ▸ 已归档（2）                                                                 │
└───────────────────────────────────────────────────────────────────────────────┘
```

- 列 = 生命周期（`PlanStatus`），**5 列**：讨论中 / 已定稿 / 执行中 / 已完成 / 已取消。
  > 修订说明：早期草稿写「4 列、已完成不占列」，与 M1（完成是**手动**动作）冲突——手动标记完成后必须有个地方看得见它、才能点「归档」。因此 `completed` 占一列；真正把方案移出主视图的是**归档**（AR1，`archivedAt` 非空 → 进底部「已归档」区）。
- **`draft` 阶段的方案在主列里只是占位**：`plan.md` 仍在被会话更新，唯一动作是预览/删除。
- **子方案归属**（阶段三）：子方案缩进/分组在其主方案下方，显示「↳ 主方案名」；阶段一没有子方案，此处理留给后续。

### 4.2 卡片内容（方案级）

阶段一实际实现（看板卡片）：

- 方案名
- 议题编号 chips（状态色：done 绿 / 有未满足前置 黄 / 失败红 / 其他灰）
- **进度条**：`done 议题数 / 总议题数`（派生，非存储）
- **依赖摘要**：`等 N 项`（未满足前置数，方案内与跨方案合并计数）
- **「可标记完成」提示徽章**（仅 `executing` 且全部议题 `done` 时出现；派生，不代改状态）
- 「未开始」徽章（该方案还没有任何议题任务）；已挂分支批时显示批次徽章
- 操作（hover）：预览 / **标记完成**（仅 `executing`）/ **重开** / **归档**（仅 `completed`）/ **取消方案** / **删除**（二次确认）

> **不做生命周期徽章**：卡片已经落在对应的生命周期列里，再挂一枚 `PlanStatus` 徽章是同一信息的重复。仅在**已归档**列表里显示状态（那里没有列上下文）。
>
> **阶段一不含**：生成待办、追加议题（阶段三）、`⚠ 前置异常` 标红（依赖门禁阶段二的 D12）。生成待办仍走「预览方案」→ `PlanPreviewPanel`。

### 4.3 卡片展开（议题任务级）

点开方案卡片 → 展开该方案的议题任务列表，每行显示：

| 议题 | 任务状态 | 依赖 Checklist（前置编号 + 是否满足） | 操作（跳转 / 忽略依赖 / 取消等待） |

> 这样「每个任务的进度和依赖情况」在看板内直接可见，不必进任务详情——正好承载依赖门禁方案里列表行放不下的完整 Checklist（`TaskList.tsx` 用固定行高虚拟滚动，不能做可展开行）。

### 4.4 入口

- 项目栏（`ProjectRailActions`）已有「任务看板」入口（`OPEN_KANBAN_VIEW_EVENT`）；方案看板并列加一个入口，或把两个看板做成同一浮层的两个 Tab（推荐后者，避免入口膨胀）。
- 欢迎页 / 云效视图也可提供入口（跨项目总览，决策 S1）。
- 「已归档」区默认折叠，由一个可展开的计数条（如「已归档 5」）进入。

## 5. 追加议题 = 子方案（依赖主方案议题）

### 5.1 为什么这个模型成立

之前判死「往已有方案追加议题」的三个硬问题，在「追加 = 新建子方案」下全部消解：

| 原问题 | 子方案模型下 |
|---|---|
| `plan.issues` 创建后不可变，没有并入入口 | **不改主方案**，新议题进**新方案**的 `issues`（新建即合法） |
| 执行任务 prompt 是生成时冻结的内联快照，重写 `plan.md` 不更新它 | 子方案有自己的 `plan.md` 与 prompt，主方案 `plan.md` 与在跑任务 prompt **零改动** |
| 会引入「新议题成为已在跑议题前置」的反向依赖不可满足 | 依赖方向单一：子方案 → 主方案（后置依赖前置），不会反向 |

### 5.2 数据模型

`Plan` 增一个字段表示归属关系：

```ts
export interface Plan {
  // …现有字段…
  /** 主方案 id：本方案是它的追加子方案（一次追加的一批议题合成，决策 A2）。
   *  依赖关系不由此字段决定，而是由 deps.json 逐议题判定（决策 B2'）。 */
  parentPlanId?: string;
}
```

- 一棵「方案树」：主方案 = 根；一次追加动作 = 挂一个子方案（**一批议题进同一个子方案**，决策 A2）。
- 子方案内部仍是普通方案：有自己的 `plan.md`、`deps.json`（既表达这批议题**彼此之间**的依赖与顺序，也表达对**祖先方案议题**的依赖）。
- `parentPlanId` 的用途：看板呈现归属（「↳ 主方案名」）+ **解析校验时界定合法引用范围**（祖先链内议题编号合法）。它本身**不代表依赖**，仅提供层级上下文。
- `plans.json` 与 `storage.rs` 的 `Plan` 结构体**必须同步**（否则字段序列化时静默丢失）。

### 5.3 依赖判定（决策 B2'：agent 按议题分析，无依赖直接放行）

子方案**不采用"等整个主方案完成"**（原 X1 已废弃），而是逐议题判定：

1. **分析**：讨论阶段，agent 依据**主方案内容 + 本次追加内容**自行判定——追加的每个议题**是否依赖主方案中的某些议题**。有则把那些议题编号写进该议题的 `dependsOn`；**没有依赖就不写**（不是"默认依赖全主方案"）。
2. **契约扩展**：`deps.json` 的 `dependsOn` 允许引用**祖先方案（主方案及其父链）**的议题编号。这是对现有契约的放宽——现状是"引用本方案外的编号一律丢弃并告警"（`planDeps.ts` 的 `unknownDependency`），需改为"允许引用祖先链内的编号，仅拒绝真正未知的编号"。
3. **门禁**：仍是纯状态派生、逐议题判定——某追加议题被阻塞，当且仅当它 `dependsOn` 的**具体议题任务**未 `done`（`done` 算满足，`failed`/`cancelled`/`interrupted` 不放行，任务缺失按 missing 处理）。
4. **无依赖 → 直接放行**：`dependsOn` 为空即不阻塞，点开始立即启动（与"无依赖任务行为不变"一致）。

**收益**：追加议题只等它**真正依赖的那几个**主方案议题，而不是等整个主方案；同时也消除了 M1 的连带风险（门禁不再依赖"用户记得点标记完成"这个人工动作）。

**关键实现发现——改动比预想小得多**（已核对既有实现）：

| 环节 | 是否需要改 | 原因 |
|---|---|---|
| `evaluateTaskGate`（门禁判定） | **不用改** | `buildTaskBySerial` 遍历**全部**任务、不过滤 `planId`；跨方案编号能直接查到主方案任务。只要图里带上这条边，门禁自动生效 |
| `topoSortPlanIssues`（方案内定序） | **不用改** | 现有实现 `if (member.has(dep)) count += 1` 已忽略集合外的依赖——跨方案边天然不干扰本方案排序 |
| `parsePlanDeps`（解析校验） | **需改** | 唯一改动点：`unknownDependency` 的判定从"不在本方案内"放宽为"不在本方案 ∪ 祖先链内" |
| 讨论 prompt / 技能契约 | **需改** | prompt 要注入主方案议题清单（编号 + 标题 + 状态）；技能契约（SkillHub）要说明 `dependsOn` 可引用主方案议题 |

**前置条件**：`buildTaskBySerial` 用议题编号作全局键，要求**同一编号在存活方案中唯一**——这由既有的 `collectOccupiedYunxiaoWorkitemIds` / `isYunxiaoWorkitemImported`（一个议题只被一个存活方案或任务占用）保证，无需额外校验。

**边界情形**：

- 被依赖的主方案议题**尚未生成待办**（无任务）→ 按 `missing` 处理：**不静默等待**，标红并提供"忽略依赖仍开始"。
- 被依赖的主方案议题任务 `failed`/`cancelled`/`interrupted` → 按 `abnormal` 处理（同上）。
- 上述两类与依赖门禁方案的 D12 共用一套处理与通知逻辑。

### 5.4 追加的交互流程（建议）

1. 在方案看板的方案卡片上点「追加议题」。
2. 弹云效议题选择器（复用 `YunxiaoView` 的列表 / 筛选），**多选**；**已占用议题不可选**（`collectOccupiedYunxiaoWorkitemIds` / `isYunxiaoWorkitemImported` 自动排除）。
3. 选中的**整批议题进同一个子方案**（`parentPlanId` = 当前方案，决策 A2），走**讨论链路**产出子方案自己的 `plan.md` + `deps.json`。
   - 讨论 prompt 需**注入主方案议题清单**（编号 + 标题 + 状态），并明确要求：只在实际存在前置关系时写入 `dependsOn`，**没有依赖就不要写**（决策 B2'）。
   - 替代方案：跳过讨论直接生成待办（复用主方案统筹）——见 §8 C。
4. 子方案定稿 → 生成待办；启动门禁逐议题按 `deps.json` 判定（跨方案边直接指向主方案议题任务，§5.3）。
5. 看板上子方案以「↳ 主方案名」呈现，缩进或分组在主方案下方；若在等主方案的某个议题，卡片显示「⏳ 等 QHDK-XXX（主方案）」。

## 7. 与「依赖门禁」方案的关系

两份方案是**互补**的，建议一起考虑但可分切片落地：

- **依赖门禁方案**（`yunxiao-plan-deps-gating-v1.md`）解决「**同一方案内**的议题按依赖串行」。
- **本方案**解决「**方案的聚合视图与生命周期**」+「**跨方案的追加与依赖**」。

看板的「依赖摘要」「议题级 Checklist」直接复用门禁方案的派生物（`evaluateTaskGate` / 等待角标 / 队列定序），不需要第二套逻辑。

**依赖顺序（已定 E2/P1）**：**先做「只读看板」**——即本方案的**第一阶段**（看板 + 生命周期 + 手动标记完成/重开 + `cancelled` 留存态 + 归档 + 进度与依赖摘要展示）；**依赖门禁与串行调度放第二阶段**（看板第一阶段的「依赖摘要」先用简单派生；`waiting_deps` 与 `evaluateTaskGate` 接入后自然细化）；**追加子方案放第三阶段**。

> 这样安排的依据：看板是独立可交付价值、直接缓解"没有整体视图"，且不依赖门禁骨架；追加（子方案）依赖 `parentPlanId` + 跨方案依赖判定，必须跟在门禁之后。

## 8. 已定决策索引

> **全部已定**（2026-09-14）：A2 · M1 · B2' · D-b · C1 · R1 · E2 · F1 · L1+L4 · P1 · AR1 · S1 —— 均见 §3.3 决策表。
> 原 §8「待拍板歧义」逐条已收敛，下列保留各条的结论索引。

### A. 追加粒度 → **已定 A2**

一次追加的一批议题**合成一个子方案**（不是一议题一子方案）。理由：「一次追加 = 一次决策」，同批议题放进一个子方案才能表达它们**彼此之间**的依赖与顺序（一议题一方案下无法互相依赖）。

### B. 依赖语义 → **已定 B2'**

原选项中 **B2**（可指定依赖父方案中的某些议题）方向正确，但**分析者改为讨论 agent 自行判定**、且**无依赖即放行**（决策 B2'，§5.3）。B3（子方案之间互相依赖）属后续增强，本期不做。

### C. ~~追加议题是否要重新走讨论链路~~ → **已定 C1**

**走讨论链路**：子方案有自己的 `plan.md` + `deps.json`。理由：B2' 要求由 agent 读主方案 + 追加内容分析依赖，这些产出必须有落盘处；且与「一方案一 `plan.md`」的既有契约一致。

### E. ~~落地顺序~~ → **已定 E2**

**先做「只读看板」**（方案看板 + 生命周期 + 手动标记完成，不涉及追加与跨方案依赖），再做依赖门禁与追加。看板是独立可交付价值，不依赖门禁骨架。

### F. ~~`cancelled` 是否改为留存态~~ → **已定 F1**

**改为可查留存态**：保留方案记录与目录，看板提供「已取消」列/区，可查看与重开；**删除**降级为显式单独操作（现 `delete_yunxiao_plan` 保留给"刻意删除"）。既有的 `collectOccupiedYunxiaoWorkitemIds` 已排除 `cancelled` 方案占用议题，逻辑天然兼容。

### D. ~~多级追加时依赖可引用的祖先范围~~ → **已定 D-b**

**允许引用整条祖先链**（父、祖父…）的议题编号。既然依赖已由 agent 按内容自行分析，就应允许它引用任何**确实相关**的祖先议题；限制到直接父方案会造出"想引用祖父议题却写不进去"的人为障碍。

实现要点：解析校验时由 `parentPlanId` 向上遍历得到祖先链（纯内存、需防环）；合法引用集合 = 本方案议题 ∪ 祖先链各方案议题。

### G. 跨方案等待在 UI 上如何呈现（**实现细节待细化**，非架构分歧）

等待中的追加议题需要让用户一眼看出**它在等谁**（可能是主方案的某个议题），才能判断该去推进哪个任务。候选：

- 任务列表行角标沿用「等 N 项」，悬停显示具体编号（含主方案议题，可用「QHDK-XXX（主方案）」标注来源）；
- 看板 / 任务详情的等待 Checklist 里，跨方案前置作为普通条目列出，但标注其**所属方案**（便于定位）并提供跳转；
- 若被依赖的主方案议题**尚未生成待办**（`missing`）或**异常**（`abnormal`），按依赖门禁方案的 D12 处理：标红 + 通知一次 + 提供「忽略依赖仍开始」。

> 这一项与「依赖门禁」方案的 D12（前置异常通知）合并设计，避免两套通知逻辑。**注意**：由于 B2' 已把依赖判定从"人工标记完成"解耦，"等主方案被标记完成"这类基于人工动作的等待**不再存在**，G 的范围因此收窄为"等主方案的具体议题任务"。

## 9. 附：为什么「追加 = 新方案」比「往主方案塞议题」更优（决策备忘）

1. **不破坏已定稿契约**：主方案 `plan.md` 是讨论产出的定稿快照；追加不应改写它（否则与已生成任务的冻结 prompt 不一致）。
2. **依赖方向天然合法**：后追加的议题只能依赖先前的（新 → 旧），不会出现「新议题成为已跑议题的前置」这种不可满足的反向依赖。
3. **复用现有链路**：子方案就是普通方案，`PlanPreviewPanel` / `GeneratePlanTodosDialog` / `deps.json` 全部复用。跨方案依赖的改动面经核对极小——门禁判定 `evaluateTaskGate` 与方案内定序 `topoSortPlanIssues` **都不用改**，只需放宽 `parsePlanDeps` 的越界校验（允许引用祖先议题）+ 讨论 prompt 注入主方案议题清单（见 §5.3）。
4. **可审计**：方案树保留了「主方案 → 追加方案」的演进历史，比把议题混在一份文件里更可追溯。
